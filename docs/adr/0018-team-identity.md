# 0018. 팀 이름·도시·약어 — 팀 레코드 직접 쓰기 (시험)

- 상태: 승인 (시험 단계 — 저장 후 유지 여부 확인 필요)
- 날짜: 2026-10-15

## 맥락
- 정관장·SK 는 Chicago Bulls·Atlanta Hawks 자리를 쓰고 있다(ADR-0015).
- MyNBA 팀 이전(Relocation)은 미국 등 미리 정해진 도시만 고를 수 있고, 팀명을 직접 입력할 수 없다(사용자 확인).
- 2KVenueLab 은 팀명·도시·약어 쓰기를 잠가 두었다("locked in 2.1").
  - 대신 probe 코드에 팀 필드 정의가 있다.

  | 필드 | 위치(TeamRecord 기준) | 크기 |
  |---|---|---|
  | team_name | +0x2E2 | UTF-16 50B (25자) |
  | city_name | +0x314 | 36B (18자) |
  | city_short_name | +0x338 | 14B (7자) — 화면 약어 |

- 같은 고정 칸 UTF-16 방식인 선수 이름은 쓰기 → 저장 → 재로드가 성공했다.

## 결정
- 팀 데이터에 `game_identity`(영문 도시·팀명·약어)를 두고, `kbl2k venuelab apply` 가 팀 레코드에 쓴다.
  - 선수 이름과 같은 방식: 실제 이전 바이트 읽기 → 쓰기 → 다시 읽기
- 사용자 지정 이름:

  | KBL 팀 | 도시 | 팀명 | 약어 |
  |---|---|---|---|
  | 안양 정관장 | Anyang | Red Boosters | JKJ |
  | 서울 SK | Seoul | Knights | SK |

- 이름을 바꾼 뒤에도 다음 실행에서 팀을 찾도록, 교체 전 이름(`nba_slot`)과 새 이름 둘 다로 찾는다.

## 결과 / 확인할 것
- 시험 항목:
  1. 쓰기 → 저장 → 로스터 재로드 후 이름이 유지되는가
  2. 빠른 게임 팀 선택, 경기 중 점수판·해설에 반영되는가
- 일부 화면(로고, 해설 음성, 점수판 그래픽)은 다른 데이터를 써서 바뀌지 않을 수 있다.
- 유지되지 않으면 이 ADR 을 '실패'로 바꾸고 다른 방법을 찾는다.

## 시험 결과 (2026-10-15)
- 쓰기: 두 팀 × 3필드, 6개 모두 성공(readback 확인). 같은 이름의 클래식 팀은 건드리지 않았다.
- 저장: 커스텀 로스터 `RosterNBA0001` 에 저장했다. 게임 화면에 Anyang Red Boosters / Seoul Knights 로 표시된다(사용자 확인).
- 남은 확인:
  - 로스터 재로드 후 유지
  - 빠른 게임 팀 선택 화면
  - 경기 중 점수판(약어)

## 재로드 결과 (2026-10-15) — 저장 유지 실패
- 커스텀 로스터를 다시 불러오면 팀명이 Chicago Bulls / Atlanta Hawks 로 돌아간다(사용자 확인).
- 쓴 위치는 VenueLab 팀 블루프린트(TEAMNAME +0x2E2 wstring 24, CITYNAME +0x314, CITYSHORTNAME +0x338)와 같다.
  - 위치 오류가 아니라, 로스터를 불러올 때 NBA 팀 이름을 다시 채우는 것으로 추정한다.
  - 예: 팀 번호 기반 고정 이름표, 또는 "이전된 팀" 표시가 필요한 구조
- 선수 이름(같은 고정 칸 방식)은 유지된다. 팀 이름만 유지되지 않는다.
- 상태: **저장 방식은 실패.** 현재 세션 안에서는 표시된다(메모리).
- 대안:
  1. 로스터를 불러올 때마다 팀 이름만 다시 쓰기(빠른 전용 명령)
  2. Bulls/Hawks 이름 그대로 두기(로고만 KBL)
  3. 추가 분석(별도 과제)

## 분석 1: 커스텀 로스터 저장·재로드 비교 (2026-10-15, `kbl2k venuelab capture-team/diff-team`)
- 같은 TeamRecord(0xC71C4420)의 쓴 직후(r2)와 저장·재로드 후(r3)를 비교했다.
  - 바뀐 구간은 **이름 3개뿐**이다: +0x2E2 팀명, +0x314 도시, +0x338 약어 → Bulls / Chicago / CHI
  - 나머지 레코드는 동일하다.
- 해석: 커스텀 로스터 저장은 NBA 팀 이름을 보존하지 않는다(저장하지 않거나, 로드 시 내장 이름으로 덮어씀).
  - 레코드 안에 이미 켜진 별도 플래그는 없다.
- r1(재로드 전) 캡처는 메모리 위치가 달라(0xC8FD4420) 포인터 값만 대량으로 달랐다. 비교에서 제외했다.
- 다음: 실험 B(MyNBA Team Relocation 전후 비교)로, 이름이 유지되는 팀에서 이름 외에 함께 바뀌는 필드를 찾는다.

## 분석 2: MyNBA 이전(Relocation) 비교 (2026-10-15, 실험 B·C)
- Bulls 를 MyNBA 에서 Denver 로 이전한 전(m1)·후(m2)를 비교했다. 이름 외에 함께 바뀐 구간:
  - +0x314/+0x338/+0x346: 도시·약어·주 약어 문자열
  - +0xE98 (16바이트): 0 → 값. 이전 도시 ID 로 추정
  - +0x1314: `03 00 03 00` → `ff ff ff ff`
  - +0x13B4, +0x13C4: 도시 관련 데이터·실수값
  - +0x140B: `01` → `11`. 0x10 비트를 "이전된 팀" 표시로 추정(미검증)
- 실험 C: 이전된 MyNBA 에 팀명(Red Boosters)을 쓰고 저장·재로드했다.
  - 팀명은 **유지**된다. 화면 표시: "Denver Red Boosters", 로고 RB(ADR-0019)
  - 도시는 이전 도시(Denver)로 표시된다. 도시 이름은 도시 ID 로 정해지는 것으로 추정한다.
- 결론
  - 커스텀 로스터: 팀 이름이 저장되지 않는다(분석 1).
  - MyNBA: 이전한 팀은 팀명이 저장된다. 도시는 이전 목록(미국 도시)에서만 고를 수 있다.
- 같은 실험에서 발견한 별도 문제(선수 데이터):
  - 나이가 틀리다. 생년월일을 한 번도 쓰지 않았다.
    - VenueLab 블루프린트에 생년월일 필드가 있고 쓰기·복원 검증됨(`write_readback_ok`)으로 표시돼 있다:
      BIRTHYEAR +0x10A(12비트, 시작 0), BIRTHDAY +0x10C(5비트, 시작 1), BIRTHMONTH +0x343(4비트, 시작 4)
  - MyNBA 로스터 화면의 포지션이 우리가 정한 값과 다르다. 원인 미확인.

## 후속: 생년월일 쓰기 추가 (2026-10-15)
- `venuelab apply` 가 선수별로 생년월일 3필드를 쓴다(docs/2k26-player-fields.md).
- 안전장치: 현재 값을 먼저 읽어 연도 1950~2015, 월 1~12, 일 1~31 로 해석될 때만 쓴다.
  - 해석되지 않으면 형식 가정이 틀린 것으로 보고 그 선수는 건너뛴다(보고서 `stage=birth, status=skipped`).
- 확인할 것: dry-run 출력의 "현재" 값이 원래 NBA 선수의 실제 생년월일과 맞는가 → 형식 검증
- 형식 검증 (dry-run `apply-dryrun-20261015-133259`): 원래 선수 값이 실제 생년월일과 일치했다
  (예: Giddey 2002-10-10, Buzelis 2004-10-13, Okongwu 2000-12-11). 연도 그대로, 월 1~12, 일 1~31 확인.
- 적용 (`apply-write-20261015-133820`): 92개 쓰기 모두 `write_readback_ok`(생년월일 86 + 팀 이름 6).
  커스텀 로스터에 저장했다(사용자).
- 커스텀 로스터 화면의 포지션은 정한 값과 맞다(사용자 확인).
  → 앞서 MyNBA 에서 포지션·나이가 틀린 것은 그 MyNBA 를 예전 로스터로 만들었기 때문으로 추정한다.

## MyNBA 팀명 유지 확인 + 분석 3: 이전 도시 표시 (2026-10-15)
- 커스텀 로스터로 MyNBA 새로 시작(판타지 드래프트 끔) → 나이·포지션 정상.
- Bulls → Virginia Beach 이전 후 `venuelab apply --apply --alias "Chicago Bulls=Virginia Beach Bulls"` → 저장·재로드해도
  **"Virginia Beach Red Boosters" 유지**(사용자 확인). 이전하지 않은 Hawks 는 Atlanta Hawks 로 돌아갔다.
- 도시 표시는 도시 테이블에서 온다(읽기 전용 캡처 `m4_named`):
  - 팀 +0xFD0 = 도시 레코드 포인터, 팀 +0xE98 = 도시 ID(도시 레코드 +0x38 의 8바이트 두 덩어리를 바꾼 순서)
  - 도시 레코드(간격 0x80): +0x00 약어 UTF-16("VIR"), +0x0E 도시 이름 ASCII 18바이트 칸, +0x20 주 약어
  - 팀 레코드의 도시 문자열(+0x314)은 "Anyang" 으로 저장돼 있지만 화면에는 쓰이지 않는다.
- 결정: `kbl2k venuelab city <팀> <도시> [--apply]` 로 도시 테이블의 이름을 메모리에서 바꾼다.
  - 안전장치: 팀의 도시 ID 와 도시 레코드 ID 가 맞을 때만 쓴다. 이전하지 않은 팀은 거부한다.
  - 도시 테이블은 게임 데이터로 보이므로 세이브에 남지 않을 것으로 예상한다 → 게임을 켤 때마다 실행(확인 필요).
  - 같은 도시로 이전한 다른 팀도 같은 이름으로 보인다.
- 시험 1: 도시 테이블 이름만 Anyang 으로 바꿈(`write_readback_ok`) → **화면은 그대로 Virginia Beach.**
- 메모리 문자열 검색(읽기 전용)으로 찾은 다른 사본:
  - 경기장 레코드(팀 +0xFC8 → +0x82 도시 UTF-16 24자, "United Center"/"arena_003_int" 와 함께) — 이전 시 바뀐 칸
  - "Virginia Beach"+"Bulls" UTF-16 구조 2곳(용도 미상), 도시 선택 목록 사본, 도시 테이블 사본 2곳
- 시험 2: `venuelab city` 가 경기장 레코드 도시 칸도 함께 바꾸도록 확장(모양 확인: +0xBA "arena_").
- 시험 2 결과: 도시 테이블 + 경기장 레코드를 바꿔도 화면은 **그대로 Virginia Beach**(사용자 확인).
- 결정 (2026-10-15): 도시명 작업은 **보류**한다. MyNBA 표시는 "Virginia Beach Red Boosters" 로 둔다.
  - 남은 후보: "Virginia Beach"+"Bulls" UTF-16 구조 2곳, 도시 선택 목록 사본, 도시 테이블 사본 2곳
  - `venuelab city` 명령은 남겨 두되 효과 없음(위 두 칸만 바꿈)을 명시한다.
  - 우선순위: 비주얼(코트·유니폼·얼굴) 먼저.
